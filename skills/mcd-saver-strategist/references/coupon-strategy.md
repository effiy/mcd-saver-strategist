# 优惠券建模与省钱策略

`optimizer.py` 把麦当劳五花八门的优惠统一抽象成 **5 类券**。理解这套抽象，
才能把 MCP 返回的真实券正确地映射进去。

## 一、5 类券

| type | 语义 | 关键字段 | 例子 |
|---|---|---|---|
| `item_price` | 单品改价：把某商品价格改成固定值 | `item_codes`, `override_price` | 巨无霸专享价 ¥18.9 |
| `percent` | 单品折扣：对匹配商品打折 | `item_codes`, `discount_pct` | 中薯条 5 折 |
| `threshold` | 满减：小计达标才减 | `min_spend`, `discount` | 满 35 减 7 |
| `bundle_price` | 组合价：每组各挑 1 个，打包固定价 | `groups`, `price` | 1+1 随心配 ¥12.9 |
| `free_gift` | 赠品：达标送商品，不影响价格 | `min_spend`, `gift_codes` | 满 20 送香芋派 |

## 二、券类型判定规则

MCP 返回一张券时，按以下顺序判断它属于哪一类：

1. 券面含"买A送B / 赠品 / 免费得" → `free_gift`
2. 券面含"满 X 减 Y" → `threshold`
3. 券面含"1+1 / 随心配 / 套餐价 / 任选 N 件 X 元" → `bundle_price`
4. 券面是"某单品 X 元" → `item_price`
5. 券面是"某商品 X 折" → `percent`

判不准时，**降级为 `threshold` 或忽略该券**，并在回复里说明「该券规则无法自动核算，
已按单点计」，绝不猜一个价格。

## 三、叠加与互斥规则（`coupon_conflict`）

模型采用保守的叠加策略，宁可少省也不多算：

- **`stackable: false` 的券与任何券互斥**（麦当劳多数单品券、套餐券不叠加）。
- **两张 `threshold` / `free_gift` 之间可叠加**（不同门槛的满减可共存）。
- **作用于同一商品的两张券互斥**（不能把同一份薯条打两次折）。
- 拿不准 `stackable` 时一律填 `false`。

> 结果偏保守是**有意设计**：算出的价格必须 ≤ 用户实际支付价，
> 宁可少报优惠，也不给用户一个到店里付不出来的"假便宜"。

## 四、省钱策略（优化器会自动命中，这里说明它为什么有效）

1. **组合价优先于单点**：`1+1 随心配` 这类券用固定价覆盖两件高价商品，通常是最优解。
   优化器会自动把组合覆盖到**每组里最贵的那件**，把便宜件留在外面。
2. **凑单满减要考虑边际成本**：为了用「满 35 减 7」而加购一件 ¥9 的东西，
   净效果是 9-7=+2 元 → 优化器**不会**选它；如果加购 ¥5 的东西，净省 2 元 → 会选。
   `notes` 字段会明确提示"为了用券加购了 X"。
3. **赠品券是白送的加分项**：不改变总价，只在 `gifts` 里体现，用来提升方案吸引力。
4. **先领券再优化**：必须在优化前调用 `auto-bind-coupons`，否则券池不全，
   算出的"最优"是伪最优。

## 五、搜索规模控制

组合优化天然是 NP 难，代码用三层剪枝把规模压到可实时求解：

1. 每个「想吃的」只保留最多 `MAX_CANDIDATES_PER_WANT`(=4) 个候选商品。
2. 菜篮最多加购 2 件互补商品，且每件只在最便宜的 6 件里挑。
3. 单方案最多叠加 `MAX_COMBO_COUPONS`(=3) 张券，且先按可适用性预筛券池。

因此一次求解通常只需评估几十~几百个方案，毫秒级返回。

## 六、边界情况

- **无解**：预算/热量过严时返回空方案，`format_report` 会提示放宽条件。
- **缺营养数据**：`calories` 置 0，热量约束自动失效，需在回复中说明。
- **门店缺货**：以 `calculate-price` / `query-meal-detail` 的实时结果为准，
  若某商品下架，用 `query-meals` 重新取数后再优化一次。
